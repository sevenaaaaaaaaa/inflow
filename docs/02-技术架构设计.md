## 1. 设计约束与原则

来自本机两个自研系统的架构哲学（这是"家族风格"，必须延续）：

| 原则 | 来源 | 在 Insight Flow 中的落地 |
|---|---|---|
| 文件优先、无重中间件 | MFlow："文件 + 状态机 + 定时任务"，无常驻 DB/消息队列 | SQLite(WAL) + Markdown/JSON 文件存储；调度用 APScheduler（单进程线程）或系统 cron，不引入 Kafka/Celery |
| 状态机管理流程 | MFlow 12 阶段状态机 + 事件流 | 监控任务、深度报告、动作验证均用显式状态机 + `events.jsonl` 事件流 |
| 钩子 + 退出码做质量门 | MFlow 4 道 bash hook | 报告生成/洞察推送前置校验 hook（如：洞察无 evidence 则阻断推送） |
| 零构建链可用 | OpenFlow：SSR + 原生 JS，无 webpack | 控制台用 FastAPI + Jinja2 SSR + htmx/原生 JS（V2 可选升级轻前端） |
| 插件权限声明 + 静态校验 | MFlow plugin_check 六项检查 | 同构的 manifest 校验器 `insflow plugin check` |
| 密钥加密、审计、SSRF 防护 | OpenFlow Secrets/AuditLog/conn_request | 对齐实现（见 §8 安全） |
| CLI > MCP 的务实偏好 | MFlow docs | CLI 与 MCP 并重：CLI 供人/脚本，MCP 供 Agent 生态（OpenFlow AgentRuntime 需要） |

技术栈选型：**Python 3.12 + FastAPI + SQLite(WAL) + APScheduler + Jinja2/htmx**。选 Python 的决定性理由：MFlow 插件规范是 Python（`collect(cfg)`），Insight Flow 的数据源插件可直接被 MFlow 复用/互借鉴，双方生态合并而非分裂。

## 4. 核心实体模型

```sql
-- 概要 schema（SQLite，完整版随 M0 迁移脚本定稿）
workspaces(id, name, stage,            -- stage: S0|S1|S2|S3, 由成熟度引擎写入
           maturity_level,             -- L0..L4
           settings_json)

sources(id, workspace_id, plugin_id,   -- 已安装数据源实例
        config_enc,                    -- 凭据引用（保险库外键，加密）
        quota_ledger_json,             -- 配额账本：调用数/费用/熔断阈值
        status)

monitors(id, workspace_id, kind,       -- kind: keyword|competitor_site|brand_mention|journey...
         target_json, schedule_cron, last_run_at, state)  -- 状态机：idle→running→ok|error

raw_records(id, workspace_id, source_id, monitor_id, kind, payload_json,
            captured_at)               -- 原始采集留存（可追溯证据）

metrics(id, workspace_id, entity_type, -- 归一化指标时序：site/keyword/competitor/topic
        entity_id, metric, value, dim_json, ts)

insights(id, workspace_id, type, title, summary,
         severity, confidence, evidence_json, models_json,
         actions_json,                 -- recommended_actions
         stage_tags_json, status,      -- new→acknowledged→actioned→verified|dismissed
         created_at, verified_at)

actions(id, workspace_id, insight_id, action_type,   -- mflow.create_content|openflow.automation|...
        target_ref, params_json, state,              -- pending→dispatched→done|failed
        dispatched_at, result_json,
        verify_window_until, baseline_json)          -- 回流验证基线

feedback(id, workspace_id, action_id, metric, before, after, delta, verdict, evaluated_at)
```

## 5. 插件系统（四类插件）

### 5.1 设计目标

1. 与 MFlow 插件规范**同构**（manifest.json + entry.py + 约定函数 + 权限声明），使插件作者一次学习两边通用；
2. 一切上游数据源、洞察模型、执行通道皆插件，核心零硬编码供应商；
3. 静态校验器 `insflow plugin check` 把关后才能被调度器自动执行。

### 5.2 manifest.json 规范

```json
{
  "id": "dataforseo-serp",
  "type": "source",                      // source | model | action | template
  "name": "DataForSEO SERP API",
  "version": "1.0.0",
  "entry": "entry.py",
  "permissions": ["network", "credentials:dataforseo"],
  "config": {
    "login": {"desc": "DataForSEO login email", "required": true, "secret": false},
    "password": {"desc": "API password", "required": true, "secret": true}
  },
  "provides": {                          // source 专用：能力声明，供模型路由匹配
    "metrics": ["serp_organic", "serp_features", "ai_overview"],
    "engines": ["google"],
    "latency": "standard|priority|live",
    "cost_hint": "0.0006 USD/SERP standard"
  }
}
```

### 5.3 约定函数（按 type）

```python
# type: source —— 采集数据，返回归一化前的标准信封
def collect(cfg: dict, ctx: CollectContext) -> dict:
    return {
        "source": "dataforseo-serp",
        "kind": "serp_organic",
        "captured_at": "...",
        "items": [...],
        "cost": {"units": 0.06, "currency": "USD"}   # 必填：进配额账本
    }

# type: model —— 消费指标，产出洞察（引擎会先跑质量门）
def evaluate(ctx: ModelContext) -> list[dict]:   # 每个 dict 即一条 Insight 草稿
    ...

# type: action —— 执行落地动作
def execute(action: dict, ctx: ActionContext) -> dict:
    return {"ok": True, "ref": "mflow:loop:8f3a", "detail": "..."}

# type: template —— 报告模板（单 JSON，含 Jinja2 段落 + 数据绑定声明）
```

### 5.4 校验器（对齐 MFlow plugin_check 六项 + 扩展）

`insflow plugin check plugins/sources/dataforseo-serp`：

1. manifest 必填字段与类型枚举；2. 目录名 = id；3. entry 存在；4. 约定函数存在且签名正确；5. **无明文密钥**（secret 类配置不得出现在代码/默认值）；6. permissions 声明覆盖实际 import 的能力（网络库/凭据读取静态扫描）；7.（扩展）`provides.cost_hint` 存在则强制走配额账本。

未过检的插件：可安装、可手动触发查看错误，但**不会被调度器自动执行**（与 MFlow 工作台行为一致）。

## 6. Skill 系统（Agent 能力层）

Skill 与插件分工：**插件 = 确定性能力**（采集/模型/动作），**Skill = Agent 的方法论**（怎么分析、怎么写报告）。

格式（跨工具兼容：Claude/Cursor/OpenFlow SkillSystem 均可识别的 Markdown+YAML）：

```markdown
---
name: competitor-move-analysis
description: 竞品异动深度分析：输入竞品 ID 与时间窗，输出动机推断与我方应对建议
triggers: [竞品, competitor, 异动]
inputs: {competitor_id: string, window_days: int = 7}
tools: [db.query, source.call:serper, source.call:firecrawl, web.fetch]
output_template: reports/templates/competitor-move.md
---

# 执行步骤
1. 读取该竞品时间窗内的全部 monitor 事件与 diff 快照
2. 用 Serper 检索该竞品近期新闻/公告交叉验证
3. 按《动机分类法》(定价/产品/渠道/组织) 归类每次异动
4. 对每个异动给出：影响评估(高/中/低) + 置信度 + 我方动作建议(引用动作库)
5. 输出必须含 evidence 引用（快照 ID / API 记录 ID），否则 quality gate 会阻断
```

内置首批 Skill（对应 PRD AG-3）：`competitor-move-analysis`、`traffic-attribution-diagnosis`、`voice-of-market-mining`、`journey-gap-analysis`、`growth-experiment-design`（ICE 评分）、`weekly-brief-writer`。

## 7. 调度与状态机

### 7.1 调度中心

- 单进程 APScheduler（`BackgroundScheduler`）+ 可选导出系统 crontab（与 MFlow launchd/systemd 模式兼容）；
- 任务类型：`monitor.run`（采集）、`model.run`（模型评估）、`report.build`、`action.dispatch`、`feedback.evaluate`、`quota.audit`；
- **依赖编排**：采集完成 → 触发依赖该指标的模型 → 洞察产出 → 触发订阅的报告与告警（事件驱动，复用 `events.jsonl` 总线）；
- 熔断：每个 source 实例的配额账本超阈值（金额/次数）自动暂停并告警。

### 7.2 动作验证状态机（回流闭环的关键）

```
action: pending → dispatched → done ─┬─→ verifying → verified(effective|neutral|harmful)
                                     └─→ failed(重试×3 → dead)

验证逻辑：dispatched 时记录 baseline_json（GSC 点击/GA4 转化/排名基线）
verify_window_until 到期 → feedback.evaluate 拉取对比 → 写 feedback + 更新模型效果分
```

## 8. 安全设计

| 项 | 设计 | 对标 |
|---|---|---|
| 凭据保险库 | AES-GCM 加密落盘 `data/vault.json`，主密钥 `INSFLOW_MASTER_KEY`（环境变量，未设则 fail-closed）；界面/日志只显尾四位 | OpenFlow `Secrets.php` |
| API 认证 | 多 Key 体系：key+secret、按 Key 授权 scope、到期、启停、IP 白名单 | OpenFlow `ApiKeyAuth` |
| Webhook 签名 | 出站 HMAC-SHA256(body, secret) + 时间戳防重放；重试退避 1m/5m/30m/2h + 死信文件；入站 `/api/v1/ingest` 同规格验签 | OpenFlow WebhookSystem/InboundReceiver |
| SSRF 防护 | 所有插件出站请求经统一 `safe_request()`：私网地址黑名单、重定向复核、超时与大小上限 | OpenFlow `conn_request` |
| 插件沙箱 | 权限声明制 + 静态校验；V2 考虑 subprocess 隔离运行不可信插件 | MFlow plugin_check + permissions |
| 审计 | `events.jsonl` 记录登录/密钥变更/插件安装/动作派发/外部推送，不可变追加 | OpenFlow AuditLog |
| RBAC | Owner/Admin/Analyst/Viewer；MCP 工具逐个 scope（read/write）校验 | OpenFlow McpGuard |

### 9.2 MCP Server（工具清单）

`list_insights / get_insight / run_diagnosis / ask_analyst / list_competitors / get_competitor_timeline / get_maturity / list_monitors / trigger_playbook / get_feedback_stats`

- 传输：stdio（本地）+ HTTP/SSE（远程，走多 Key 认证）；
- 消费方：OpenFlow AgentRuntime（`mcp:*` 工具通道）、Claude/Cursor/任意 MCP 客户端。

### 9.3 Webhook 事件

`insight.created / monitor.alert / report.ready / action.executed / feedback.received / quota.warning` — HMAC 签名，订阅制，退避重试 + 死信。


## 11. 关键技术决策记录（ADR 摘要）

| # | 决策 | 理由 | 放弃的替代 |
|---|---|---|---|
| ADR-1 | Python 而非 PHP/Node | MFlow 插件生态是 Python，插件规范可同构复用；数据科学库（pandas/statsmodels）直接可用 | PHP（OpenFlow 同栈，但采集/分析生态弱） |
| ADR-2 | SQLite 而非 Postgres 起步 | 家族哲学（零依赖自托管）；监控型负载写放大可控；预留 `DATABASE_URL` 切换点 | Postgres（V2 多租户时切换） |
| ADR-3 | 搜索源抽象层为 M0 必做 | Bing 2025-08 退役、Google CSE 2027-01 停服——供应商不可绑定 | 直连单一供应商 |
| ADR-4 | SSR + htmx 而非 SPA | 零构建链家族风格；单人可维护；报告场景交互简单 | React/Vue SPA |
| ADR-5 | MCP 一等公民（尽管 MFlow 偏好 CLI） | OpenFlow AgentRuntime 以 `mcp:*` 消费外部工具，这是洞察被自主 Agent 消费的关键通道；同时保留全量 CLI | 仅 CLI |
| ADR-6 | 第三方主力选 DataForSEO 而非 Semrush API | Semrush 被 Adobe 收购后条款不确定 + $549/月门槛 + units 黑盒；DataForSEO 按量透明（SERP $0.6/千次）；Semrush/Ahrefs 作为企业档可插供应商 | Semrush API 为主 |
