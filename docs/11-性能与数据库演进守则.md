# Insight Flow 性能与数据库演进守则

> v1.0（2026-09-16）。**直接借鉴 OpenFlow 的教训与方案**（见其 docs/EVOLUTION.md）。
> 适用：私有化单机 / 云托管 / 自托管个人。

---

## 1. 三条铁律（OpenFlow 血泪教训）

| # | 教训 | Insight Flow 的落地 |
|---|------|---------------------|
| 1 | **心跳/埋点无节制 → 63 万行垃圾数据被清空** | 前端自动刷新降频（延迟 60s、间隔 120s、上限 20 次、隐藏暂停）；事件流写入降频合并；事件流 30 天轮转 |
| 2 | **写放大比表大小更该监控**（写放大不随表长增长，不会先预警再撞墙） | 不看"表多大"，看 **每次写摊多少读 / p95 耗时 / 单租户月度成本** |
| 3 | **换底座不换楼**（产品逻辑不因存储升级重写） | 所有 DB 访问收敛在 `Store` 一层；预留 `INSFLOW_DB_PATH` / `DATABASE_URL` 切换点 |

## 2. SQLite 基线（对齐 OpenFlow `Database.php`）

```python
# insflow/core/store.py::connect()
PRAGMA journal_mode=WAL      # 并发读写（OpenFlow 同款）
PRAGMA busy_timeout=5000     # 防锁等待失败（OpenFlow 同款）
PRAGMA foreign_keys=ON
PRAGMA synchronous=NORMAL    # WAL 下安全且快
PRAGMA temp_store=MEMORY     # 临时表走内存
PRAGMA cache_size=-20000     # 20MB 页缓存
PRAGMA mmap_size=268435456   # 256MB 内存映射
```

**维护**：每日 09:10 事件轮转 + 备份；WAL 通过 `PRAGMA wal_checkpoint(TRUNCATE)` 收敛（备份流程内触发）。

## 3. 缓存（对齐 OpenFlow `Cache.php`）

| 层 | 实现 | 说明 |
|---|---|---|
| 默认 | 进程内 TTL 缓存 + **单飞**（防击穿） | 零依赖，驾驶舱聚合 90s |
| 可选 | **文件后端**（`INSFLOW_CACHE=file`） | 跨进程共享、重启不丢（对齐 OpenFlow FileCache） |
| 未来 | Redis 驱动 | 多机部署时切换（对齐 OpenFlow RedisCache） |

用法等价于 OpenFlow 的 `Cache::remember`：`cache.get_or_compute(key, factory, ttl)`。
**失效**：`cache.invalidate("cockpit:sentiment")` 按前缀精确清理。

## 4. 频率治理（对齐 OpenFlow 心跳降频）

| 对象 | 守则 |
|---|---|
| 前端自动刷新 | 默认**关闭**；开启后延迟 60s 起、间隔 120s、单会话上限 20 次、页面隐藏暂停 |
| 监控任务 cron | **最小间隔守卫**（创建时校验）：site_change ≥30min、keyword ≥6h、topic ≥30min、brand_mention ≥1h、journey ≥6h |
| 事件流写入 | 同 (workspace, type, 业务键) 在窗口内**合并为一条**（monitor.run_finished 5min、source.collected 3min…）；关键事件（quota.exceeded 等）不降频 |
| 指标写入 | 同 monitor + 同小时窗口 + 同指标 → `INSERT OR IGNORE`（幂等，重跑零重复）|
| 事件保留 | 30 天轮转（`EventBus.rotate`），每日自动 |

## 5. 量化演进触发器（对齐 OpenFlow"不量错对象"）

> OpenFlow 的修正：**写放大的开销不随表长增长**，所以它不会先预警再撞墙。
> 该量的是下面这些（Insight Flow 在运维驾驶舱实时展示）：

| 指标 | 健康值 | 触发动作 |
|---|---|---|
| **单次写入摊了多少读** | ≈1 | >10 排查是否有循环查询/N+1 |
| **DB 查询 p95** | <20ms | >100ms 查索引/加缓存 |
| **页面 p95** | <300ms | >800ms 定位慢页面（`/console/cockpit/ops` 列出 Top 慢路径） |
| **缓存命中率** | >70% | 过低说明 TTL 太短或键设计过细 |
| **每租户月度数据源成本** | 在毛利内 | 超限即配额熔断 + 提示升级 |
| metrics 行数 | <200 万 | ≥80% 时评估：分区/冷层/换底座 |
| events 行数 | <50 万 | 轮转策略收紧（30→14 天） |
| 月活用户（单租户） | <1 万 | >1 万 → 该租户独立优化 |
| 部署形态 | 单机 | 多机/多租户 → Tier 2/3 |

**监控入口**：`/console/cockpit/ops` → 性能与容量面板（p95 / 命中率 / DB 大小 / 表增长 vs 阈值）。

## 6. 数据库切换路径（预留，不提前做）

> **对齐 OpenFlow 现状**：OpenFlow 已演进为 **SQLite/MySQL 双驱动，事件表切 MySQL**，
> SQLite 保留作辅助（画像等）。Insight Flow 采用同一路线：
> **MySQL 为主（生产/多租户），SQLite 内嵌辅助（个人/自托管零依赖）**。

```
驱动 1  SQLite（内嵌，默认）      WAL + 上述 pragma；个人/自托管零依赖
驱动 2  MySQL 5.7+（生产推荐）    INSFLOW_DB_DRIVER=mysql + MYSQL_* 配置
缓存    INSFLOW_CACHE=file        跨进程/重启不丢（对齐 OpenFlow FileCache）
冷层    预留 DuckDB/ClickHouse    亿级事件聚合（多租户后）
```

**已实现**（`insflow/core/db/`）：
- 方言层 `dialect.py`：占位符 `?↔%s`、`INSERT OR IGNORE ↔ INSERT IGNORE`、
  `strftime ↔ DATE_FORMAT`（周格式 `%W ↔ %x-%v`）、部分索引能力标记
- 后端 `backends.py`：`SQLiteBackend`（aiosqlite）/ `MySQLBackend`（aiomysql，可选依赖）
- MySQL schema `schema_mysql.py`：InnoDB + utf8mb4、**索引列一律 VARCHAR**（不能索引裸 TEXT）、
  **无部分索引**（改用完整 UNIQUE KEY，仅对全新库成立——与 OpenFlow"MySQL 从零开始"一致）
- 切换方式：`INSFLOW_DB_DRIVER=mysql`，配置命名对齐 OpenFlow `mysql_*` 约定
- CLI：`insflow db status`（驱动/容量/p95）、`insflow db migrate`（按驱动建表）

**OpenFlow 迁移三坑（已在本项目规避）**：
1. `INSERT OR IGNORE`（SQLite）↔ `INSERT IGNORE`（MySQL）不能共用 → 按驱动分支
2. MySQL `ONLY_FULL_GROUP_BY` 严格模式 → 聚合查询的 GROUP BY 覆盖全部非聚合列
3. MySQL 5.7 无部分索引 → 去重索引降级为完整唯一键（仅全新库可行）

**切换点**：`Store` 是唯一 DB 访问层——换驱动只切后端与方言，业务代码零改动（"换底座不换楼"）。
**SQLite 重定位**：`INSFLOW_DB_PATH=/data/insflow.db`。

## MySQL 迁移第 6 坑：DELETE 的子查询不能引用目标表（2026-09-17 实测）

`DELETE FROM feedback WHERE id IN (SELECT f.id FROM feedback f JOIN ...)` 在 SQLite 正常，
MySQL 直接报 `(1093, "You can't specify target table 'feedback' for update in FROM clause")`。

**做法**：先 `SELECT` 出主键，再用 `IN (?, ?, …)` 参数化删除（跨驱动一致，且避免拼接）。
`insflow demo clear` 已按此实现（`insflow/engine/demo.py`）。

## 预聚合与沙箱（2026-09-17 落地）

- **汇总表**：`metric_daily`（workspace/metric/day/entity/dim → sum/avg/max/n）。
  长窗口（≥30 天）趋势查询优先读汇总，未命中自动回退明细；`insflow rollup build` 幂等重建，
  调度每日 09:05 执行。实测演示数据 30 天：明细 1717 行 → 汇总 1927 行，覆盖 24 个指标。
- **维度索引注意**：唯一键含 `dim_key`（province），否则带维度的行会互相覆盖
  （SQLite 静默忽略、MySQL 唯一键报错）；采集侧窗口键由 `dim_window_key()` 生成。
- **只读 SQL 沙箱**：白名单表 + 每条表引用改写成 `(SELECT * FROM t WHERE workspace_id = ?)`
  子查询（MySQL 要求派生表别名，已处理），强制 LIMIT 500；实测拒绝 DDL/DML/系统表/多语句。
- **删除的子查询**：MySQL 不允许 `DELETE ... WHERE id IN (SELECT ... FROM 同表)`，
  改「先查主键再 `IN (?, …)`」（`demo clear` 已按此实现）。

## 权限与缓存的相互作用（2026-09-17 实测修复）

1. **预聚合快路径不得绕过权限**：`metric_daily` 不承载 `rls_policies` / 主体白名单，
   因此 `metric_series` 在存在 policy/entity_allow 时必须走明细（安全 > 性能）。
2. **聚合缓存键必须含权限签名**：驾驶舱 TTL 缓存的 key 追加 `_auth_sig(policy,
   entity_allow)`（sha1 前 10 位）。否则宽权限用户先访问会把数据灌进缓存，
   窄权限用户命中同一 key → **越权读到不该看的数据**。
3. **SSE 连接**：`/api/v1/stream` 逐事件检测 `request.is_disconnected()` 并及时退出，
   避免连接泄漏；反代需 `X-Accel-Buffering: no`（已随响应下发）。
