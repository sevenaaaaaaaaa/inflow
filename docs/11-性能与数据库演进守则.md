# Insight Flow 性能与数据库演进守则

> v1.0（2026-09-16）。**直接借鉴 OpenFlow 的教训与方案**（见其 docs/EVOLUTION.md）。
> 适用：私有化单机 / 云托管 / 自托管个人。

---

## 1. 三条铁律（OpenFlow 血泪教训）

| # | 教训 | Insight Flow 的落地 |
|---|------|---------------------|
| 1 | **心跳/埋点无节制 → 63 万行垃圾数据被清空** | 前端自动刷新降频（延迟 60s、间隔 120s、上限 20 次、隐藏暂停）；事件流写入降频合并；事件流 30 天轮转 |
| 2 | **写放大比表大小更该监控**（写放大不随表长增长，不会先预警再撞墙） | 不看"表多大"，看 **每次写摊多少读 / p95 耗时 / 单租户月度成本** |
| 3 | **换底座不换楼**（产品逻辑不因存储升级重写） | 所有 DB 访问收敛在 `Store` 一层；预留 `INSFLOW_DB_PATH` / `DATABASE_URL` 切换点 |

## 2. SQLite 基线（对齐 OpenFlow `Database.php`）

```python
# insflow/core/store.py::connect()
PRAGMA journal_mode=WAL      # 并发读写（OpenFlow 同款）
PRAGMA busy_timeout=5000     # 防锁等待失败（OpenFlow 同款）
PRAGMA foreign_keys=ON
PRAGMA synchronous=NORMAL    # WAL 下安全且快
PRAGMA temp_store=MEMORY     # 临时表走内存
PRAGMA cache_size=-20000     # 20MB 页缓存
PRAGMA mmap_size=268435456   # 256MB 内存映射
```

**维护**：每日 09:10 事件轮转 + 备份；WAL 通过 `PRAGMA wal_checkpoint(TRUNCATE)` 收敛（备份流程内触发）。

## 3. 缓存（对齐 OpenFlow `Cache.php`）

| 层 | 实现 | 说明 |
|---|---|---|
| 默认 | 进程内 TTL 缓存 + **单飞**（防击穿） | 零依赖，驾驶舱聚合 90s |
| 可选 | **文件后端**（`INSFLOW_CACHE=file`） | 跨进程共享、重启不丢（对齐 OpenFlow FileCache） |
| 未来 | Redis 驱动 | 多机部署时切换（对齐 OpenFlow RedisCache） |

用法等价于 OpenFlow 的 `Cache::remember`：`cache.get_or_compute(key, factory, ttl)`。
**失效**：`cache.invalidate("cockpit:sentiment")` 按前缀精确清理。

## 4. 频率治理（对齐 OpenFlow 心跳降频）

| 对象 | 守则 |
|---|---|
| 前端自动刷新 | 默认**关闭**；开启后延迟 60s 起、间隔 120s、单会话上限 20 次、页面隐藏暂停 |
| 监控任务 cron | **最小间隔守卫**（创建时校验）：site_change ≥30min、keyword ≥6h、topic ≥30min、brand_mention ≥1h、journey ≥6h |
| 事件流写入 | 同 (workspace, type, 业务键) 在窗口内**合并为一条**（monitor.run_finished 5min、source.collected 3min…）；关键事件（quota.exceeded 等）不降频 |
| 指标写入 | 同 monitor + 同小时窗口 + 同指标 → `INSERT OR IGNORE`（幂等，重跑零重复）|
| 事件保留 | 30 天轮转（`EventBus.rotate`），每日自动 |

## 5. 量化演进触发器（对齐 OpenFlow"不量错对象"）

> OpenFlow 的修正：**写放大的开销不随表长增长**，所以它不会先预警再撞墙。
> 该量的是下面这些（Insight Flow 在运维驾驶舱实时展示）：

| 指标 | 健康值 | 触发动作 |
|---|---|---|
| **单次写入摊了多少读** | ≈1 | >10 排查是否有循环查询/N+1 |
| **DB 查询 p95** | <20ms | >100ms 查索引/加缓存 |
| **页面 p95** | <300ms | >800ms 定位慢页面（`/console/cockpit/ops` 列出 Top 慢路径） |
| **缓存命中率** | >70% | 过低说明 TTL 太短或键设计过细 |
| **每租户月度数据源成本** | 在毛利内 | 超限即配额熔断 + 提示升级 |
| metrics 行数 | <200 万 | ≥80% 时评估：分区/冷层/换底座 |
| events 行数 | <50 万 | 轮转策略收紧（30→14 天） |
| 月活用户（单租户） | <1 万 | >1 万 → 该租户独立优化 |
| 部署形态 | 单机 | 多机/多租户 → Tier 2/3 |

**监控入口**：`/console/cockpit/ops` → 性能与容量面板（p95 / 命中率 / DB 大小 / 表增长 vs 阈值）。

## 6. 数据库切换路径（预留，不提前做）

```
Tier 1   SQLite（当前）            WAL + 上述 pragma，单机/个人/中小企业足够
Tier 1.5 SQLite + 文件缓存         INSFLOW_CACHE=file（多 worker / 重启不丢）
Tier 2   MySQL / Postgres          DATABASE_URL 切换；Store 查询层适配（对齐 OpenFlow EventStore 双驱动）
Tier 3   ClickHouse / DuckDB 冷层  亿级事件聚合（未来多租户）
```

**切换点**：`Store` 是唯一 DB 访问层——切换时只改 `connect()/查询方言`，业务代码零改动（"换底座不换楼"）。
**显式迁移**：`INSFLOW_DB_PATH=/data/insflow.db` 可把库放到独立盘。
